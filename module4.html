Project Management Plan

A plan to create an audit-ready inventory of university software using an existing licensed platform.

Author: Tobi Adedoyin · Budget: $85,000 · Delivery target: seven months after the revised schedule

← All Modules

1. Project Rationale

The university currently lacks a complete inventory of the software it owns, licenses, rents, or manages, creating a problem for Legal and the annual license audit. Within seven months after the revised schedule, the project will deliver a usable software-tracking system on an existing university-licensed platform. The system will collect and organize required software information from all fourteen academic and administrative units, including software type, developer, version, licensing information, and departments using the software. The project will remain within the $85,000 budget. Success will be measured by all fourteen units submitting and reviewing their required information, the IT director accepting the system, and documented ownership and maintenance procedures being transferred to IT before the moved-up audit.

2. Scope and Boundaries

3. The Six Phases

Phase / TimingActivities, Owner, and Exit Condition
Initiation — Month 1Confirm the audit requirement, $85,000 budget, timeline, team availability, stakeholders, and boundaries. Owner: Project Manager. Exit: CIO approves the charter and scope.
Definition — Months 1–2Gather requirements from IT, Procurement, General Counsel's office, the 14 units, and the spreadsheet owner. Owner: Project Manager. Exit: Required fields and reporting requirements are approved.
Design — Months 2–3Define the collection, validation, and reporting process using the existing licensed platform. Owner: Project Manager and IT developers. Exit: Design is approved and no new platform exception is required.
Development — Months 3–6Coordinate development, prepare required fields, begin data collection, and document procedures. Owner: IT developers and Project Manager. Exit: Core audit-required functions are operational and initial data is entered.
Implementation — Months 6–7Pilot the system, collect remaining audit-required information, correct errors, and validate results. Owner: Project Manager and IT Director. Exit: All 14 units have submitted and reviewed required information and IT approves the system for audit use.
Follow-Up — Month 7Transfer ownership, document maintenance procedures, identify the system owner and backup, and complete final audit documentation. Owner: Project Manager and IT Director. Exit: IT accepts ownership and the audit-ready inventory is complete.

6. Timeline and Dependencies

The critical path is requirements approval → design approval → audit-required development → completion of information from all 14 units → validation → IT acceptance. These tasks cannot slip without threatening the new seven-month deadline. The student worker's Month 6 departure is also a key dependency.

7. Response to the Complication

The Implementation phase absorbs most of the compression because the pilot and rollout can be narrowed to the information required for the audit. Development will continue to protect the core system, while Follow-Up will remain short but sufficient for ownership transfer.

The project will protect the information directly required for the audit: software ownership/status, licensing information, software type, developer, versions, and departments using the software. The project will cut or defer machine-level installation information and installation dates from the first release. Those items will move into a Phase 2 enhancement owned by IT after the audit.

The loss of approximately three developer-weeks will be addressed using the remaining $85,000 budget. Contracted assistance may be used for defined development, data preparation, or cleanup tasks. This does not change the project scope; it provides additional capacity for the reduced audit-focused deliverable.

The CIO will receive the revised delivery commitment first. The IT Director will then confirm acceptance requirements and ownership responsibilities. The fourteen units and spreadsheet owner will be notified immediately because their reporting schedules are affected. Procurement and General Counsel's office will be told which information is protected for the audit and which information has been deferred.

The project will say no to a new platform, software replacement, nonessential automation, and the full machine-level inventory in the first release. Those requests would consume resources needed for the audit-required system. The deferred work will be documented as a Phase 2 effort rather than silently added back into the current project.

8. Where the Model Strains

The six phases provide useful control points, but following them completely sequentially creates risk after the audit moves forward. Data collection, documentation, and validation can overlap with development once their requirements are stable. The project should retain formal phase approvals while allowing compatible activities to run in parallel when doing so does not create rework. This flexibility is necessary because the project has lost approximately three developer-weeks of capacity and the student worker leaves at Month 6. The revised approach keeps the six-phase structure while using controlled overlap, reduced scope, and possible contracted support to protect the audit-required deliverable.
